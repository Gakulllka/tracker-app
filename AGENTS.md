## 1. Контекст проекта

Delta Tasker — внутренний трекер задач для небольшой команды, ориентировочно до 30 пользователей.

Приложение используется для:

- ведения задач по доменам;
- распределения прав пользователей по ролям и доменам;
- месячного планирования;
- учёта плановых и фактических часов;
- ведения бэклога, вопросов и комментариев;
- формирования отчётов, презентаций, Excel и PDF;
- синхронизации изменений между пользователями.

Это не публичный массовый SaaS. Высокая нагрузка не является приоритетом. Главные приоритеты:

1. не потерять данные;
2. не сломать права доступа;
3. не изменить существующее поведение без прямого запроса;
4. обеспечить возможность простого отката;
5. объяснить результат пользователю без технического жаргона.

## 5. Порядок работы над каждой задачей

### Шаг 1. Понять запрос

До изменения кода кратко сформулируй:

- что должно измениться;

- затрагивается ли база данных;
- затрагивается ли синхронизация;
- какие сценарии нужно проверить.

Если запрос пользователя можно выполнить несколькими способами, выбери самый простой и наименее рискованный.

### Шаг 2. Изучить существующую реализацию

Перед редактированием:

1. найди все файлы, связанные с функцией;

Не начинай писать код после просмотра только одного компонента.

### Шаг 3. Оценить риск

Определи уровень изменения:

#### Низкий риск

- текст интерфейса;
- визуальное отображение;
- локальный компонент;
- фильтр или сортировка без изменения сохранения данных.

#### Средний риск

- изменение формы;
- новое поле интерфейса;
- изменение Zustand-store;
- изменение API без изменения схемы базы;
- изменение импорта или экспорта.

#### Высокий риск

- любое изменение `prisma/schema.prisma`;

- изменение авторизации;
- изменение ролей;
- изменение доменных прав;
- изменение синхронизации;
- изменение логики удаления;
- изменение формата JSON, хранящегося в базе;
- массовое обновление существующих записей.

Для высокого риска сначала остановись и отдельно опиши:

- что именно будет изменено;
- какие данные могут пострадать;
- нужен ли backup;
- как выполнить откат;
- можно ли решить задачу без изменения базы.

## 6. Правила работы с базой данных

База данных является самой ценной частью проекта. Любое изменение базы считается потенциально опасным.

Используется PostgreSQL через Prisma.

Основная схема находится в:

```text
prisma/schema.prisma
```

Подключение использует переменные:

```text
DATABASE_URL
DIRECT_URL
```

### 6.1. Никогда не выполнять без прямого разрешения

Запрещено автоматически запускать:

```bash
npm run db:reset
prisma migrate reset
prisma db push --force-reset
```

Также запрещено без явного разрешения:

- удалять таблицы;
- удалять колонки;
- очищать таблицы;
- использовать `TRUNCATE`;
- выполнять массовый `DELETE`;
- выполнять массовый `UPDATE` без ограничивающего условия;
- изменять production-базу для эксперимента;
- запускать seed, который перезаписывает реальные данные;
- делать миграцию без предварительного анализа существующих данных.

Команда `db:reset` уничтожает данные. Никогда не предлагай её как обычный способ исправления ошибки.

### 6.2. Перед изменением схемы

До изменения `prisma/schema.prisma`:

1. объясни, зачем это необходимо;
2. проверь, можно ли решить задачу без миграции;
3. перечисли затрагиваемые модели и поля;
4. определи, есть ли существующие данные в этих полях;
5. опиши совместимость старого и нового кода;
6. подготовь способ отката;
7. потребуй актуальный backup production-базы.

### 6.3. Безопасные изменения схемы

Обычно безопаснее:

- добавить nullable-поле;
- добавить поле с корректным значением по умолчанию;
- добавить новую таблицу без изменения старых;
- добавить индекс после оценки влияния;
- сначала добавить новое поле, перенести данные, и только в отдельной задаче отказаться от старого.

Обычно опаснее:

- переименовать поле напрямую;
- изменить тип существующего поля;
- сделать nullable-поле обязательным;
- удалить поле;
- изменить формат JSON-строки;
- изменить внешние ключи и каскадное удаление;
- менять `onDelete`;
- менять идентификаторы записей.

### 6.4. Миграции

Для локальной разработки может использоваться:

```bash
npm run db:migrate
```

Но перед запуском проверь, какую базу указывает `DATABASE_URL`.

Никогда не запускай development-миграцию, пока не ясно, что подключение ведёт к локальной или тестовой базе.

Для production:

- не используй `prisma migrate dev` как команду деплоя;
- не применяй миграцию вслепую;
- сначала просмотри сгенерированный SQL;
- убедись, что SQL не удаляет данные;
- сделай backup;
- только затем применяй миграцию штатным способом выбранной платформы.

### 6.5. `prisma db push`

Команда:

```bash
npm run db:push
```

не должна использоваться как универсальное решение.

Она допустима только если:

- точно известно, к какой базе идёт подключение;
- это тестовая или локальная база;
- изменение не уничтожает данные;
- пользователь понимает последствия.

Для production предпочтительны контролируемые миграции.

### 6.6. Изменение данных

Любой скрипт массового изменения данных должен:

- сначала работать в режиме предварительного просмотра;
- показывать количество затронутых строк;
- иметь точное условие отбора;
- не менять записи, которые не относятся к задаче;
- быть повторно запускаемым без порчи данных;
- выводить результат выполнения;
- иметь обратный скрипт или понятный способ восстановления.

Перед массовым изменением сначала выполнить безопасный запрос чтения и показать, какие записи будут затронуты.

### 6.7. Удаление данных

В проекте задачи и элементы бэклога используют мягкое удаление через поле `deleted`.

Не заменяй мягкое удаление физическим `DELETE`, если это прямо не запрошено.

Учитывай tombstone-записи и синхронизацию. Удалённая запись может быть нужна клиентам, чтобы понять, что её надо удалить локально.

### 6.8. JSON в строковых полях

Некоторые данные сохраняются как JSON внутри строковых полей, например:

- `monthlyPlans`;
- `commentLog`;
- `extra`;
- `answer`;
- поля AI-инсайтов.

При изменении этих структур:

1. не меняй формат старых записей без миграционного плана;
2. поддерживай чтение отсутствующих полей;
3. используй безопасный `JSON.parse` с обработкой ошибок;
4. не удаляй неизвестные поля при сохранении;
5. проверяй обратную совместимость;
6. сохраняй старую структуру, если новое поле можно добавить необязательно.

Нельзя просто заменить формат JSON и ожидать, что старые данные автоматически подойдут.

### 6.9. Числа, хранящиеся как строки

Поля `planH` и `factH` сейчас могут храниться как строки.

Не меняй их тип в базе без отдельной задачи и миграционного плана.

При работе с ними:

- проверяй преобразование в число;
- обрабатывай пустую строку;
- не сохраняй `NaN`;
- не допускай случайной конкатенации строк;
- сохраняй формат, который ожидает существующий интерфейс и экспорт.

## 7. Правила ролей и доступа

Права доступа являются критической бизнес-логикой.

Текущая модель включает глобальную роль пользователя и отдельные права редактирования доменов.

Ожидаемые роли:

- `admin` — полный доступ и админ-панель;
- `editor` — редактирование всех доменов без админ-панели;
- `viewer` — просмотр без редактирования;
- `member` — редактирование только разрешённых доменов;
- `guest` — просмотр без выдачи прав.

Права отдельного домена хранятся через `DomainEditor`.

### При любом изменении прав проверь

1. Кто может видеть домен.
2. Кто может редактировать домен.
3. Кто может создавать задачи.
4. Кто может изменять задачи.
5. Кто может удалять задачи.
6. Кто может выдавать права.
7. Кто может одобрять запросы доступа.
8. Что происходит с заблокированным пользователем.
9. Что происходит с архивным доменом.
10. Проверяет ли сервер права независимо от интерфейса.

Никогда не полагайся только на скрытую кнопку в интерфейсе. API обязан самостоятельно проверять права.

Не меняй значение существующих ролей и не объединяй роли без прямого запроса.

## 8. Правила синхронизации

Синхронизация является сложной и рискованной частью проекта.

Текущая логика может использовать:

- клиентскую временную метку `ts`;
- last-write-wins;
- мягкое удаление через `deleted`;
- имя последнего редактора `updatedBy`.

При любом изменении синхронизации:

1. изучи весь маршрут синхронизации целиком;
2. проверь чтение и запись задач;
3. проверь чтение и запись бэклога;
4. проверь фильтрацию по доменным правам;
5. проверь обработку удалённых записей;
6. проверь поведение старого клиента;
7. не меняй формат ответа API без обновления всех потребителей;
8. не удаляй tombstone раньше, чем это безопасно;
9. не заменяй частичное обновление полной перезаписью без анализа;
10. проверь сценарий двух пользователей, редактирующих одну запись.

Особенно проверь сценарий:

- пользователь A меняет часы;
- пользователь B меняет комментарий;
- оба сохраняют;
- изменение одного пользователя не должно неожиданно исчезнуть.

Если текущая архитектура не умеет объединять такие изменения, не скрывай ограничение. Объясни его пользователю.

## 9. Правила изменения API

При изменении API:

- сохраняй существующий формат ответа, если его изменение не требуется;
- не переименовывай поля без обновления всех клиентов;
- валидируй входящие данные;
- возвращай понятные ошибки;
- не отправляй пользователю внутренний stack trace;
- проверяй роль и права на сервере;
- ограничивай объём массовых запросов;
- не доверяй `userId`, `role`, `username` или правам, пришедшим от клиента;
- определяй пользователя по действующей сессии.

Для нового поля предпочтительно:

- сделать его необязательным на переходный период;
- задать безопасное значение по умолчанию;
- поддержать старые запросы;
- затем отдельно обновить интерфейс.

## 10. Правила изменения интерфейса

Пользователь проекта тестирует приложение вручную и не читает код.

Поэтому:

- не меняй расположение привычных элементов без запроса;
- не переименовывай кнопки без причины;
- не скрывай действие, которое раньше было доступно;
- показывай понятное сообщение после сохранения;
- показывай понятную ошибку при сбое;
- блокируй повторное нажатие во время сохранения;
- не очищай форму при неудачной отправке;
- предупреждай перед необратимым действием;
- сохраняй введённые данные при временной ошибке;
- проверяй интерфейс на обычной ширине экрана.

Любое изменение UI должно сопровождаться короткой инструкцией ручной проверки.

## 11. Работа с большими файлами

В проекте могут быть крупные файлы, включая главную страницу и общий store.

Не переписывай большой файл целиком ради небольшого изменения.

При локальной задаче:

1. найди точный участок;
2. измени минимальное количество строк;
3. не форматируй весь файл;
4. не перемещай несвязанные функции;
5. не переименовывай переменные за пределами задачи.

Рефакторинг большого файла выполняется только отдельной задачей.

При рефакторинге:

- поведение не меняется;
- сначала добавляются или запускаются тесты;
- перенос выполняется по одному модулю;
- после каждого переноса запускается сборка;
- пользователь получает список перемещённых частей;
- откат должен быть простым.

## 12. TypeScript и качество кода

Сейчас сборка может игнорировать TypeScript-ошибки. Это не означает, что ошибки можно добавлять.

При новом коде:

- не используй `any` без крайней необходимости;
- не добавляй `@ts-ignore` как способ скрыть проблему;
- не добавляй non-null assertion `!`, если значение реально может отсутствовать;
- используй существующие типы;
- не дублируй модели данных в разных файлах;
- обрабатывай `null` и `undefined`;
- не меняй тип данных только для удобства локального кода.

Если проект уже содержит TypeScript-ошибки, отделяй старые ошибки от новых.

Нельзя заявлять, что изменение корректно, если оно добавило новые ошибки типов.

## 13. Тестирование

Пользователь не может проверить внутреннюю корректность кода, поэтому автоматические проверки обязательны там, где это возможно.

### Минимальные критические сценарии

1. Администратор может войти.
2. Обычный пользователь может войти.
3. Заблокированный пользователь не может работать.
4. Viewer не может редактировать.
5. Member может редактировать разрешённый домен.
6. Member не может редактировать чужой домен.
7. Editor может редактировать все активные домены.
8. Созданная задача остаётся после обновления страницы.
9. Изменение задачи сохраняется после синхронизации.
10. Удалённая задача не возвращается после синхронизации.
11. Архивный домен отображается только по текущим правилам.
12. Импорт не уничтожает данные молча.
13. Экспорт создаёт открываемый файл.

### После изменения базы или API

Дополнительно проверь:

- старые записи открываются;
- новые записи создаются;
- пустые необязательные поля не вызывают ошибку;
- права проверяются сервером;
- данные другого домена не изменяются;
- удаление работает по прежней модели;
- повторная отправка не создаёт нежелательные дубликаты.

### Ручная проверка

Отчёт должен содержать пошаговый сценарий, понятный человеку без знания кода:

```text
1. Войдите под пользователем с ролью member.
2. Откройте домен, где у него есть право редактирования.
3. Создайте задачу.
4. Обновите страницу.
5. Убедитесь, что задача осталась.
6. Откройте домен без права редактирования.
7. Убедитесь, что редактирование недоступно.
```

---

## 14. Backup и восстановление

Перед любым изменением высокого риска убедись, что существует актуальная резервная копия базы.

Не считай backup существующим только потому, что платформа обычно делает копии. Нужно знать:

- где хранится backup;
- когда он создан;
- как его скачать;
- как его восстановить;
- проверялось ли восстановление.

Перед миграцией в отчёте явно напиши:

```text
Требуется backup базы перед применением.
```

Если нет информации о backup, не выполняй destructive-изменение.

### Код

До изменения должен существовать commit рабочей версии.

Не смешивай несколько независимых задач в одном commit.

Рекомендуемое имя commit:

```text
fix: исправлено сохранение комментария задачи
feat: добавлена архивация пользователя
refactor: вынесен экспорт Excel без изменения поведения
```

## 15. Деплой

Перед деплоем:

1. проверить список изменённых файлов;
2. проверить, не попали ли секреты;
3. выполнить lint;
4. выполнить build;
5. выполнить доступные тесты;
6. проверить необходимость миграции;
7. проверить наличие backup;
8. записать сценарий ручной проверки;
9. убедиться, что есть способ вернуться к предыдущему deployment или commit.

После деплоя проверить:

- вход;
- загрузку доменов;
- открытие задач;
- сохранение одной тестовой задачи;
- права пользователя;
- отсутствие ошибок в серверных логах;
- экспорт, если он затрагивался;
- синхронизацию, если она затрагивалась.

Не вносить дополнительное исправление прямо в production без отдельного commit.

---

## 16. Секреты и переменные окружения

Никогда не добавляй в репозиторий:

- `DATABASE_URL`;
- `DIRECT_URL`;
- токены;
- пароли;
- приватные ключи;
- содержимое production `.env`;
- реальные резервные копии базы.

Перед commit проверь изменённые файлы на наличие секретов.

В отчёте не выводи полные значения секретов. Можно показывать только имя переменной и факт её наличия или отсутствия.

---

## 17. Что запрещено говорить пользователю без проверки

Не используй утверждения:

- всё работает;
- проблема полностью исправлена;
- данные не пострадают;
- миграция безопасна;
- сборка проходит;
- тесты проходят;
- права доступа сохранены;

если это не было реально проверено.

Используй точные формулировки:

- сборка прошла успешно;
- тест не запускался, потому что отсутствует зависимость;
- изменение проверено только статически;
- production-база не изменялась;
- миграция подготовлена, но не применена;
- риск потери данных остаётся, нужен backup.

## 18. Формат ответа перед изменением

Перед началом сложной задачи дай короткий план:

```markdown
### Что буду менять
- ...

### Что не буду менять
- ...

### Риск
Низкий / средний / высокий.

### База данных
Не затрагивается / требуется изменение схемы / требуется миграция.

### Проверки
- ...
```

Не перегружай пользователя техническими деталями. Подробности нужны только там, где они влияют на риск.

## 19. Формат итогового отчёта

После выполнения используй структуру:

```markdown
## Что сделано
Простое описание результата.

## Изменённые файлы
- `path/file.ts` — что изменено.

## База данных
- Не изменялась.
или
- Изменена модель ...
- Миграция подготовлена, но не применена.
- Перед применением требуется backup.

## Проверки
- `npm run lint` — успешно / ошибка.
- `npm run build` — успешно / ошибка.
- тесты — успешно / не запускались и почему.

## Как проверить вручную
1. ...
2. ...

## Что может пойти не так
- ...

## Как отменить
- Вернуть commit ...
- Для базы использовать ...
```

## 20. Готовый алгоритм для любой новой функции

Используй этот порядок:

1. Прочитать задачу.
2. Найти связанные компоненты, store, API и модели Prisma.
3. Описать текущее поведение.
4. Определить минимальное изменение.
5. Проверить влияние на роли.
6. Проверить влияние на домены.
7. Проверить влияние на синхронизацию.
8. Проверить влияние на импорт и экспорт.
9. Проверить, требуется ли изменение базы.
10. При изменении базы остановиться и описать риски.
11. Сделать локальное изменение.
12. Не исправлять несвязанные проблемы.
13. Запустить lint.
14. Запустить build.
15. Запустить связанные тесты.
16. Составить ручной сценарий проверки.
17. Перечислить изменённые файлы.
18. Объяснить результат простыми словами.
19. Описать откат.

## 21. Короткий обязательный промпт-контроль

Перед завершением каждой задачи ответь себе:

- Я изменил только то, что просили?
- Я не сломал права ролей и доменов?
- Я не изменил формат данных незаметно?
- Я не применил опасную команду к базе?
- Я не удалил реальные данные?
- Я проверил сборку?
- Я честно указал, что не смог проверить?
- Пользователь сможет проверить результат без знания кода?
- Пользователь сможет отменить изменение?

Если хотя бы на один вопрос ответ отрицательный, задача ещё не завершена.

## 22. Главная установка

Этот проект поддерживается человеком без навыков программирования с помощью ИИ.

Поэтому лучший результат — не самый сложный и не самый технологичный. Лучший результат:

- понятный;
- минимальный;
- проверяемый;
- совместимый с текущими данными;
- безопасный для базы;
- легко отменяемый;
- объяснённый человеческим языком.
